# Reasonix 日常开发 Skill 实操指南

> 本文档回答一个问题：**在 Reasonix 项目的日常开发中，我怎么用这套技能系统？**
>
> 这不是理论讲解。这是一个"你要加功能 / 修 bug / 重构 / 性能优化 / 审查 / 调查 / 上线 / 回滚"的全场景操作手册。
> 共覆盖 17 个场景，外加一个决策表。

---

## 快速参考卡

如果你只记得一个流程，记下面这个：

```
收到任务
    │
    ▼
┌─────────────────────────────────┐
│ 1. 对齐：/grill-with-docs        │ ← 搞清楚到底要做啥
│    → CONTEXT.md 更新术语         │
│    → ADRs 记录关键决策           │
└──────────┬──────────────────────┘
           ▼
┌─────────────────────────────────┐
│ 2. 规划：/to-spec                │ ← 写正式 spec（不重新提问）
│    → docs/specs/<功能>.md       │
└──────────┬──────────────────────┘
           ▼
┌─────────────────────────────────┐
│ 3. 拆票：/to-tickets             │ ← 拆成可执行的工单
│    → .scratch/<功能>/tickets.md │
└──────────┬──────────────────────┘
           │
           ▼  ← 对每个工单执行以下流程
┌─────────────────────────────────┐
│ 4. 构建：/implement              │
│    ├─ 读工单 → 探索代码库        │
│    ├─ /tdd (每个垂直切片)         │
│    │   ├─ 写失败测试 (red)       │
│    │   ├─ 最小实现 (green)       │
│    │   └─ 循环                  │
│    ├─ go vet 常跑                │
│    └─ /code-review (提交前)      │
└──────────┬──────────────────────┘
           ▼
           git commit
```

## 五种核心流水线

不是所有任务都走完整流程。根据任务类型选择不同的路径：

```
                    ┌─── 大功能（>3文件 / 涉及接口）
                    │   标准流程：grill → spec → tickets → implement
                    │
任务类型 ──────┬─── 小改动（≤3文件 / 不碰接口）
                    │   /grill-with-docs → /implement
                    │
                    ├─── 修 bug
                    │   小：/tdd → /code-review
                    │   难：/diagnosing-bugs → 修复 → 回归
                    │
                    ├─── 重构 / 架构改进
                    │   /improve-codebase-architecture → 讨论
                    │   → 标准流程或 expand-contract
                    │
                    ├─── 性能优化
                    │   /diagnosing-bugs(定位) → 按范围选路径
                    │
                    ├─── 依赖升级
                    │   patch: 直接改
                    │   major: expand-contract
                    │
                    ├─── 审查他人 PR
                    │   /code-review
                    │
                    ├─── 调查问题（不改代码）
                    │   不需要技能，直接问
                    │
                    └─── 配置 / infra 变更
                        不需要技能，直接改
```

## 场景一：加一个新功能（标准流程）

**例子**：给 Reasonix 加一个"自动格式化代码"的功能。

### Step 1：对齐 — `/grill-with-docs`

你在对话中告诉 agent："我想加一个自动格式化代码的功能。"

Agent 会自动检测到现有技能系统。跑 `/grill-with-docs` 后，它会：

1. 读 `CONTEXT.md`，了解现有术语（Controller、Turn、Seam 等）
2. 调用 `/domain-modeling` 逐条追问：
   - "这个命令是 TUI 里的 `/format`，还是 git hook，还是单独的 CLI 命令？"
   - "格式化所有 `.go` 文件还是只改过的？"
   - "先 `gofmt -w` 再 `goimports -w`？还是只要 gofmt？"
   - "成功静默、失败报错？"
3. 如果出现新术语（比如"批量格式化作业"），立即更新 `CONTEXT.md`
4. 如果涉及架构决策（"做成一个 Controller 方法而非直接调 gofmt"），创建 ADR
5. 一次只问一个问题，不轰炸

**完成条件**：你说"好，清楚了"。`CONTEXT.md` 已更新。所有决策分支已解决。Agent 没有开始实现。

### Step 2：写 Spec — `/to-spec`

**关键约束**：Agent 不会重新采访你——它只综合已经讨论过的内容。所以 Step 1 的对齐越充分，Step 2 的 spec 越精确。

在同一轮对话中跑 `/to-spec`。Agent 会：

1. 读代码库（如果还没读的话），找到合适的测试 seam
2. 问你这几个 seam 对不对
3. 写 spec 到 `docs/specs/auto-format.md`

Spec 包含：问题描述 → 解决方案 → 用户故事 → 实现决策 → 测试决策 → 超范围。

实现决策里不写具体文件路径（会过时），只写模块名和接口名。

**完成条件**：`docs/specs/auto-format.md` 已存在。

### Step 3：拆工单 — `/to-tickets`

跑 `/to-tickets`。Agent 会：

1. 读 spec + 代码库，找 prefactor 机会
2. 拆成 tracer-bullet 工单，例如：
   - Ticket 1：在 Controller 上暴露 `FormatAll()` 方法（阻塞：无）
   - Ticket 2：添加 `/format` slash command 入口（阻塞：Ticket 1）
   - Ticket 3：添加 go vet 集成（阻塞：Ticket 1）
3. 向你确认粒度和依赖关系
4. 写入 `.scratch/auto-format/tickets.md`

**完成条件**：`.scratch/auto-format/tickets.md` 已存在，你批准了拆票方案。

### Step 4：逐一实施 — `/implement`

对 frontier 上的第一个工单跑 `/implement`：

```
Frontier: Ticket 1（无阻塞）、Ticket 3（依赖 Ticket 1，还没到）
→ 先取 Ticket 1
```

Agent 会：

1. 读工单描述 + 验收标准
2. 读相关代码库，寻找 prefactor 机会
3. 在每个 seam 处跑 `/tdd`：写失败测试 → 最小实现 → 通过 → 循环
4. 跑 `go vet ./...` 和单文件测试
5. 跑 `/code-review`：
   - **Standards 轴**：编码约定 + 设计气味
   - **Spec 轴**：是否实现了 ticket 的需求
6. 提交到当前分支

**完成条件**：一个 ticket 完成并提交。取 frontier 上的下一个继续。

### Step 5：最终检查

所有 ticket 完成后：`go test ./...` 全过，review 已跑，功能可用。

## 场景二：修一个 Bug

**例子**：`list_sessions` 在 session 数超过 100 时崩溃。

### 快速路径（肉眼可见的根因）

直接修，跑 `/tdd`：

1. Agent 写一个重现 bug 的测试（red）
2. 修复代码（green）
3. 跑 `/code-review` 检查
4. 提交

### 困难路径（找不到原因）

1. 跑 `/diagnosing-bugs`。Agent 自动执行诊断循环：
   - **复现**：写一个确定性的失败测试
   - **最小化**：缩小触发条件——是 100 个 session 还是 100 个文件？
   - **假设**：提出具体根因假设（如"ListSessions 里 slice append 越界"）
   - **仪表化**：加日志验证假设
   - **修复**：复现变为 green
   - **回归测试**：保留测试
2. 如果诊断发现"这个 bug 之所以难修是因为模块 seam 太差"，调 `/improve-codebase-architecture`

### 间歇性 bug / 不能本地复现

- Agent 不能本地复现时，应该让你提供日志或 core dump
- 用分析日志的路径走诊断循环
- 如果"加日志 → 观察 → 修 → 验证"的周期太长，在生产环境加临时日志（但要在 ADR 里记录为什么加、什么时候删）

## 场景三：代码库健康检查

每几天跑一次 `/improve-codebase-architecture`：

1. Agent 扫描 `internal/`，找浅模块、缺失的 seam、泄漏的抽象
2. 写一份 `ARCHITECTURE-NOTES.md` 报告
3. 你挑一个候选，Agent 用 `/codebase-design` 词汇讨论设计
4. 确定方案后走 `/grill-with-docs` → `/implement`

**频率**：每 3-5 天一次，或者每次大功能完成后跑一次。

**为什么要做**：Agent 加速了代码产出，也加速了代码熵增。不像人类会自觉保持整洁，Agent 倾向于在已有模式上叠加——所以需要主动检查。

## 场景四：不确定设计方案时

你有一个状态机逻辑，"不确定这样对不对"。

1. 跑 `/prototype`
2. Agent 判断这是 **LOGIC**（逻辑/状态模型）还是 **UI**（界面）类型
3. 对于 LOGIC：写一个交互式终端程序，让你手动推状态
4. 验证后，把决策记录到 ADR 或 commit message
5. **删除原型代码**——或者把关键逻辑吸收进正式代码

**扔掉的代码永远不写测试、不处理错误边界、不持久化**。它只回答一个问题，回答完就删。

---

## 场景五：上下文窗口快满了

当前对话已经很长了，但你还没完成。

1. 跑 `/handoff "继续完成 Ticket 3 的后端逻辑"`
2. Agent 压缩当前上下文到 `.reasonix/handoffs/<timestamp>-continue-ticket3.md`
3. 新 session 中你说"读取刚才的 handoff，继续"
4. Agent 读文件，知道上下文、剩余工作和推荐技能

## 场景六：性能优化

**例子**：Controller 的 `Compose` 方法在大上下文时延迟超过 2 秒。

### 流程

1. **用 `/diagnosing-bugs` 定位瓶颈**
   - 这里的"bug"是性能回归
   - Agent 用 `go test -bench` 或 `pprof` 建立反馈回路
   - 关键：先有一个可复现的性能测试（red）

2. **按影响范围选路径**
   - 只涉及一个模块的内部实现 → 直接修，用 `/tdd` 确保不坏已有功能
   - 涉及接口变化 → 走标准流程：`/grill-with-docs` → `/to-spec` → `/implement`

3. **约束**
   - 加 benchmark 测试（不删）
   - 优化前后都要跑 benchmark，记录数据
   - 如果优化涉及权衡（更快 vs 更占内存），写 ADR

## 场景七：依赖升级

**例子**：把 `bubbletea` 从 v0.x 升到 v1.x。

### 流程

1. **评估影响范围** — Agent 用 `grep` 搜 import 路径，读 go.mod
2. **读 Breaking Changes** — 用 `research` 在后台读 changelog
3. **按影响选路径**：
   - 无 API 变化 → 直接 `go get`，跑全量测试
   - API 变化局限在一个包内 → `/implement`（一个 ticket）
   - 波及全库 → expand–contract：Ticket 1（适配器新旧并存）→ Ticket 2-N（逐包迁移）→ Ticket N+1（删除旧适配器）
4. **patch 升级一个 commit，major 升级每个 ticket 一个 commit**

## 场景八：审查他人 PR

**例子**：同事提了一个 800 行 diff 的 PR，改动涉及 `internal/agent/` 和 `internal/tool/builtin/`。

### 流程

1. **跑 `/code-review`**
   - Agent 自动检测当前 git diff
   - 两轴并行：Standards（约定 + 设计气味）+ Spec（需求实现）
   - 如果涉及 shell 调用、文件写入、token 处理，自动调内置 `security_review`

2. **如果 PR 太大**
   - > 500 行 diff → 建议 PR 作者拆小
   - > 1000 行 diff → 拆成多个 /implement 分别审查

3. **Review 自动检查清单**
   - 新增的导出函数有 Go 注释
   - 错误没有 `if err != nil { return nil }` 这种 swallow
   - 测试覆盖了新增路径
   - 没有硬编码的 token/secret
   - 日志没有打印敏感信息

## 场景九：生产事故排查

**例子**：线上用户反馈"发消息后 agent 无响应"，但本地无法复现。

### 流程

**特殊：没有代码改动，纯粹调查。不需要标准工作流。**

1. **收集现场信息**
   - 用 Agent 分析日志文件
   - 检查配置差异（线上 vs 本地）
   - 用 `research` 查已知 issue

2. **建立假设**
   - Agent 用 `/diagnosing-bugs` 的框架推理
   - 但"复现"是分析日志，不是写单元测试

3. **修复**
   - 确定根因后：小修直接 `/tdd`，大改走 spec

4. **事后记录**
   - 写 ADR 记录事故原因和修复
   - 如果有监控缺口，写一个 ticket

## 场景十：写用户文档

**例子**：为新加的 `/format` 功能写用户文档。

### 流程

1. **用 `research` 读现有文档风格**
2. 对 agent 说"把刚才讨论的格式化功能写成用户文档"
3. Agent 应**不重新提问**，直接综合已知信息

### 检查清单

- 文档里的命令示例可实际运行
- 文档引用 `CONTEXT.md` 里的术语
- 没有内部实现细节泄漏到用户文档
- 文档的路径匹配项目约定（看 README.md、docs/ 下的已有文件）

## 场景十一：新人上手

**例子**：新同事第一天，需要了解项目怎么开发。

### 流程

1. **跑 `/setup-reasonix-skills`**
   - 确认 `.reasonix/skills/` 已安装
   - 确认 `CONTEXT.md` 存在
   - 说明 user-invoked vs model-invoked

2. **新人记住 3 个核心技能**
   - `/grill-with-docs` — 开始任何工作前先跑
   - `/implement` — 开始实现时跑（它驱动 tdd + code-review）
   - `/setup-reasonix-skills` — 想不起来就重跑

3. **第一个任务示范**
   - 带新人走一遍 `/grill-with-docs` → `/to-spec` → `/implement`
   - 解释：为什么不能跳过对齐

---

## 场景十二：灰度 / Feature Flag

**例子**：新格式化功能先对 10% 用户开放。

### 流程

1. 标准流程走完设计
2. Tickets 中预留 flag 相关工单：
   - Ticket 1：添加 feature flag 配置和检查逻辑
   - Ticket 2：实现格式化功能（受 flag 保护）
   - Ticket 3：按比例打开 flag
3. **Flag 约束**
   - 从配置读取，不是 hardcode
   - 默认关
   - 写 ADR：为什么用 flag、什么时候全量、什么时候删除

---

## 场景十三：持久化 / Schema 变更

**例子**：给 session 记录加一个 `tags` 字段（JSON 数组）。

### 流程

1. 标准流程走设计
2. **使用 expand–contract**：
   - Expand：新字段和旧字段并存，读路径兼容两种格式
   - Migrate：逐批迁移旧数据
   - Contract：删除旧格式读路径
3. 写 ADR：为什么变更、迁移策略
4. 如果向后兼容有风险，写验证测试

---

## 场景十四：跨包重构

**例子**：把 `internal/skill` 的部分职责拆到 `internal/skill/loader`。

**这是波及面最广的改动类型。绝对不能跳过步骤。**

1. **`/grill-with-docs` 必须做，且比功能开发更彻底**
   - 每个被影响包的调用者都要梳理清楚
   - 当前接口的每一个调用点都要列出来

2. **`/codebase-design` 全程参与**
   - 定义新 seam 位置、接口深度
   - 使用深模块词汇：Module、Interface、Seam、Depth

3. **`/to-tickets` 用 wide refactor 模式**
   - 不能用垂直切片（重构的"价值"在整体完成后才体现）
   - expand–contract：旧接口保留 → 新接口 → 逐包迁移 → 删旧
   - 每个迁移包是独立 ticket，有明确阻塞边

4. **每个 ticket 跑 `/code-review`**
   - 重构最容易引入行为变化而不自知

## 场景十五：回滚

**例子**：昨天合入的提交在 production 触发 panic。

### 流程

1. **紧急回滚** — 不需要技能，`git revert` 直接操作
2. **回滚后调查** — 走 `/diagnosing-bugs`
3. **修复后重新提交** — 走完整流程
   - 对齐阶段要探讨"第一次为什么 panic"
   - 出问题的路径作为回归测试

---

## 场景十六：合并长周期分支

**例子**：功能分支开发了两周，main 已经前进了很多。

### 流程

1. 用 `git rebase main` 或 `git merge main`
2. 解决冲突后跑全量测试
3. 如果有新增 ADR 或 CONTEXT.md 变更，确认与 main 上的变更不矛盾
4. 如果 main 上的变更改变了被改模块的接口：
   - 用 `/codebase-design` 重新评估模块深度
   - 可能需要调整重构方案

## 场景十七：什么技能都不需要

| 操作 | 原因 |
|------|------|
| 改一个配置项的值 | 不需要对齐、spec、ticket |
| 查看日志或调试输出 | 纯读操作 |
| 问一个概念性问题 | 不是开发任务 |
| 跑已有的测试 | 不涉及改动 |
| git 操作（status, log, diff）| 不涉及行为变化 |

**判断标准**：不改变代码行为，或改变只涉及一个人一眼能看清的配置值——不需要技能。其他所有场景，至少跑 `/grill-with-docs`。

## 全场景决策表

```
任务来了
│
├─ 是 bug 吗？
│   ├─ 小 bug（肉眼可见根因）→ /tdd → /code-review → commit
│   └─ 难 bug / 间歇性 / 性能 → /diagnosing-bugs → 修复
│
├─ 是新功能吗？
│   ├─ 大功能（>3文件 / 涉及接口）→ 标准流程
│   └─ 小改动（≤3文件，不碰接口）→ /grill-with-docs → /implement
│
├─ 是重构吗？
│   ├─ 单包内部 → /grill-with-docs → /implement
│   └─ 跨包 / 涉及公共接口 → 标准流程 + wide refactor
│
├─ 是性能优化？
│   └─ /diagnosing-bugs（定位）→ 按影响范围选路径
│
├─ 是依赖升级？
│   ├─ patch → 直接改
│   └─ major（有 breaking changes）→ expand–contract
│
├─ 是合并 PR？
│   └─ /code-review（+ security_review 如果涉及安全）
│
├─ 是调查问题？（不改代码）
│   └─ 不需要技能，直接问
│
├─ 是配置 / infra 变更？
│   └─ 不需要技能，直接改
│
├─ 是写文档？
│   └─ research + 直接对 agent 说"写成文档"
│
├─ 是 Schema/持久化变更？
│   └─ 标准流程 + expand–contract
│
└─ 是灰度 / Feature Flag？
    └─ 标准流程 + flag 工单 + ADR
```

## 常见反模式

### ❌ 跳过对齐直接开干

"我已经想清楚了，不用 grill，直接开写。"

**现实**：你想清楚的是"你要什么"，不是"Agent 以为你要什么"。跳过对齐节省 10 分钟，但可能多花 2 小时重做。

### ❌ Spec 里写具体文件路径

"把 `internal/control/controller.go` 的 `Run()` 改成..."

**原因**：Spec 写好到实现之间可能隔了几天，文件路径可能变了。写模块和接口名就够了。

### ❌ 一个工单横跨多个模块

"Ticket 1：重构整个用户系统"

**原因**：一个 ticket 应该是一个垂直切片——"用户能登录"、"用户能登出"、"用户能重置密码"。每次只做一件事。

### ❌ 原型不删

"先留着，以后可能用得上"

**现实**：以后从来不会用上。它只会让新人困惑"这个 `_proto` 目录是什么？"。做完就删。

### ❌ 不用 `/code-review`

"改动就两行，不用看了"

**现实**：两行改动引起的问题多了去了。`/code-review` 除了检查 Standards，还检查 Spec——你是不是真的实现了需求。这个检查在改动小时反而最有价值，因为你最容易觉得"两行不用看"。

### ❌ 一个 session 做三个 ticket

"反正都相关，一起做了吧"

**现实**：每个 ticket 应该在一个干净的上下文窗口中完成。做 Ticket 1 时积累的中间上下文会影响 Ticket 2 的判断。做完 Ticket 1 提交，清上下文，再开始 Ticket 2。

### ❌ 把 `CONTEXT.md` 当笔记本用

往 CONTEXT.md 里写实现细节、临时笔记、TODO。

**现实**：`CONTEXT.md` 是共享词汇，不是笔记本。实现细节写进去只会让 Agent 困惑——"这个短语是指领域概念还是指技术实现？" 技术笔记写在 commit message 或代码注释里。
