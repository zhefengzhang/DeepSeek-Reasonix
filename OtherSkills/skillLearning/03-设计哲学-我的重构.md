# 我的重构：这个仓库背后的设计哲学

> 这一步最重要。我不复制作者的结构，我用我的框架重新组装。

---

## 作者给的框架

作者的组织方式：
1. 按调用方式分（user-invoked / model-invoked）
2. 按领域分（engineering / productivity）
3. 每个 skill 是一个独立的文件夹 + SKILL.md

这是给 "用户" 看的分类法——方便你浏览和安装。

## 我的重构框架

我觉得这个仓库本质上是一套 **"AI 时代的工程纪律操作系统"**，由五个层次组成：

```
┌──────────────────────────────────────────────┐
│  第五层：执行纪律                              │
│  /implement → /tdd → /code-review             │
│  约束：red-green-refactor, seam-first         │
├──────────────────────────────────────────────┤
│  第四层：规划纪律                              │
│  /to-spec → /to-tickets                      │
│  约束：vertical slice, blocking edges         │
├──────────────────────────────────────────────┤
│  第三层：对齐纪律                              │
│  /grill-with-docs, /grill-me                 │
│  约束：one question at a time, shared lang   │
├──────────────────────────────────────────────┤
│  第二层：共享词汇（vocabulary layer）           │
│  /domain-modeling, /codebase-design           │
│  约束：精确术语, deep module philosophy        │
├──────────────────────────────────────────────┤
│  第一层：基线配置                              │
│  /setup-matt-pocock-skills                   │
│  约束：issue tracker, labels, domain docs    │
└──────────────────────────────────────────────┘
```

### 这五层解决什么问题？

| 层 | 核心问题 | 没有这层会怎样 |
|----|---------|--------------|
| 1. 配置 | Agent 不知道你的项目管理工具在哪 | 写出来的东西不知道往哪发 |
| 2. 词汇 | Agent 用 20 个词说一个概念 | 废话连篇，变量命名不一致 |
| 3. 对齐 | 你以为 agent 懂了，它其实没懂 | 写出来的东西不是你要的 |
| 4. 规划 | 一个模糊的想法直接变成代码 | 写着写着发现方向错了 |
| 5. 执行 | 代码没有反馈回路 | 测试不过，质量不可控 |

## 核心洞察：为什么这比提示词更有效

提示词的问题是：它是一次性的、不可组合的、不可维护的。

Matt 这套系统的核心创新不是每个 skill 的内容，而是**技能之间的组合规则**：

```
组合规则 1：User-invoked 可以调用 Model-invoked，但不反过来
→ 保证人的控制权在编排层，agent 的控制权在实现层

组合规则 2：Stage 1-3 在一个不中断的上下文中完成
→ 磨刀、写 spec、拆 ticket 共享同一个思考过程

组合规则 3：每个 /implement 在新上下文中开始
→ 防止一个工单的实现干扰另一个

组合规则 4：垂直切片 + 阻塞边 = 可并行的执行计划
→ 只要一个工单的前置依赖完成了，就可以立即开始
```

这不是一个技能有多好，是**它们合起来形成一个系统**。

## 深层设计原则

### 原则 1：信息层级决定 Agent 行为的可靠性

```
Agent 需要的信息，按紧迫程度排：
  1. 步骤（steps）——必须按顺序执行的
  2. 内嵌参考（in-skill reference）——过程中要查阅的
  3. 外置参考（disclosed reference）——需要时才触发的
```

把不需要的东西推出核心路径，核心路径上的东西 agent 就不会错过。
把需要的东西推到外置文件，上下文窗口就更干净、agent 推理更准确。

这是**不是** token 优化——这是行为可靠性设计。

### 原则 2：每次交互的粒度是关键设计决策

什么时候拆成一个独立 skill，什么时候合并？

两个拆分的杠杆：
1. **按调用方式拆**——如果你有一个独立的触发词（leading word），且会单独用到，就拆成 model-invoked skill
2. **按顺序拆**——如果当前步骤做完后，后续步骤的可见性会让 agent 急于提前完成当前步骤（premature completion），就隐藏后续步骤

拆分的代价：user-invoked 花认知成本（你要记住），model-invoked 花上下文成本（description 常驻）。
不拆分也有代价：一个技能变得太长（sprawl），agent 在里面找路。

### 原则 3：完成标准（Completion Criterion）是核心杠杆

每一步后面写"完成标准"不是装饰。

一个**清晰的**完成标准防止 premature completion——agent 确切知道什么时候算干完了。
一个**有要求的**完成标准驱动 legwork——agent 知道要做到什么程度才够。

最强完成标准 = 可检查 + 穷尽。

可检查：agent 能判断"做完了"还是"没做完"。
穷尽：不是"列出改动"，是"每个被改的模型都检查过了"。

### 原则 4：Leading Word——用模型已经知道的概念来压缩指令

这是最巧妙的设计点之一。

不用写一长段话来描述"你要彻底检查每一条规则，不能漏掉任何一条"，用**一个模型已经理解的词**就够了。

例子：
- **relentless**（不留情面地）——比 "be thorough" 更强，后者 agent 本来就在做
- **red**（红灯）——把"bug/测试失败"这个模糊状态变成一个可观察的是/否状态
- **tracer bullet**（曳光弹）——一个完整的端到端切片，不是水平分层

这不是术语装逼。这是用模型 pretraining 中已有的模式来压 token 数、提高行为准确性。

### 原则 5：不承诺不等于不做

这个仓库有一套对 "default"（默认行为）的敏感。如果 agent 本来就会做某件事，写进 skill 就是 no-op（浪费 token）。但有些本来会做的事，因为 agent 在上下文中看到其他东西就不做了，就需要写进去。

所以每个句子都要问：**相比于默认行为，它改变了什么？**

## 我以前觉得这只是一个"prompt 合集"

重构完发现完全不是。

它是一个自省性的系统——它有一套元技能（`/writing-great-skills`）来解释自己怎么写的，有一套 GLOSSARY.md 来定义自己的术语，有一个 ADR 来记录自己的架构决策。

它告诉你不是"怎么用这些技能"，是"怎么思考这些技能"。

## 我从中学到的三件事

### 1. "Less is more" 在 Agent 指令中不是修辞，是工程

每一行不改变行为的文字都是噪音。噪音越多，agent 对重要指令的注意力越分散。

一个技能文件里每一行都要问：它改变了默认行为吗？如果删掉，agent 的行为会变吗？

### 2. 可组合性不是偶然，是设计出来的

这个系统中的 skill 之间不是"一个文件引用另一个文件"——是通过**触发词**（/name）来组合的。这意味着一份技能的内容可以藏在它自己的文件夹里，另一个技能只需要知道它的名字和什么时候调用它。

这提醒我：写 Agent 指令不是在写文档，是在设计接口（interface）。

### 3. "共享语言"在 AI 时代比在 DDD 时代更重要

DDD 说"统一语言减少团队内部的沟通成本"。
Matt 说：统一语言减少了 Agent 和人类之间的沟通成本，还减少了 Agent 的 token 开销，还让代码命名一致，还让 Agent 推理更快。

一个 `CONTEXT.md` 的 ROI 可能比整个代码库的任何模块都高。
