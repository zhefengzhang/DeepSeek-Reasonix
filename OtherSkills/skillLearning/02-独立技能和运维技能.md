## 代码库健康 — 周期性维护

### `/improve-codebase-architecture`

**解决的问题**：代码越来越烂，但没人有精力每天重构。这个技能帮你找到"深化的机会"（deepening opportunities）。

**流程**：
1. 扫描代码库，找出哪些模块可以变得更深（更多行为隐藏在更小接口后面）
2. 展示一份可视化的 HTML 报告
3. 你挑其中一个，它用 /codebase-design 词汇和 /grill-with-docs 流程来处理

**建议频率**：每几天跑一次。它不是修 bug，是预防代码熵增。

### `/codebase-design`（model-invoked）

**解决的问题**：给团队一个讨论模块设计的共享词汇表，这样不会每个人说不同的词。

核心概念——**Deep Module（深模块）**：

```
深模块 = 小接口 + 大量实现（好）
浅模块 = 大接口 + 少量实现（坏）

┌─────────────────────┐      ┌─────────────────────────────────┐
│   Small Interface   │      │       Large Interface           │
├─────────────────────┤      ├─────────────────────────────────┤
│                     │      │  Thin Implementation            │
│  Deep Implementation│      │  (Just passes through)          │
│                     │      │                                 │
└─────────────────────┘      └─────────────────────────────────┘
```

词汇表（必须精确使用，不能替代）：
- **Module** — 任何有接口和实现的东西（避免：unit, component, service）
- **Interface** — 调用者正确使用一个模块需要知道的**所有东西**（类型签名 + 不变量 + 顺序约束 + 错误模式 + 配置 + 性能特征）
- **Depth** — 每单位接口能调用的行为量
- **Seam** — 可以改变行为而无需在该位置编辑的位置
- **Adapter** — 满足 seam 处接口的具体实现
- **Leverage** — 调用者从深度获得的收益
- **Locality** — 维护者从深度获得的收益

决策规则：
- **删除测试**：如果删掉这个模块，复杂度消失了？那它就是个 pass-through。如果复杂度散布到了 N 个调用者那里？那它在干活。
- **接口即测试表面**：调用者和测试跨同样的 seam。如果你想"绕过接口测试"，模块形状大概率不对。
- **一个 adapter = 假设的 seam，两个 adapter = 真实的 seam**：没有东西真正需要变化之前，别引入 seam。

## 研究

### `/research`（model-invoked）

**解决的问题**：你想知道某个问题的答案——API 签名、文档细节、某个事实——但你自己去翻文档太花时间。

**约束**：
- 在**后台 agent** 中运行，你继续干活
- 只查**一手来源**：官方文档、源码、spec、一手 API，**不是**二手解读
- 每个 claim 都要引用来源
- 产物：一个 Markdown 文件，存在仓库里合适的地方

**使用场景**：在研究问题放在主流程的磨刀阶段之前——research 喂 thinking，不替代它。

## 跨 session 桥接

### `/handoff`

**解决的问题**：当前上下文快满了，需要在新 session 继续。

**做的事情**：
- 把当前对话压缩成一个 handoff 文档
- 保存到 OS 临时目录（不是仓库）
- 包含"推荐的 skills"段落
- 引用已有产物（spec、plan、ADR、issue、commit），不重复内容
- 脱敏

## 学习

### `/teach`

**解决的问题**：你想让 Agent 教一个技能或概念，跨越多个 session。

**约束**：
- 把当前目录当作教学 workspace
- 有完整的工作区结构：MISSION.md, lessons/, reference/, learning-records/, assets/
- 区分 **Fluency strength**（临时检索能力）和 **Storage strength**（长期保留）
- 设计原则：期望困难（retrieval practice, spacing, interleaving）
- 每节课很短，一个可完成的单位
- 知识先于技能，技能通过交互反馈循环练习

**注意**：不是简单地"给我讲一下"——是一套结构化的、session-over-session 的学习系统。它假设你真的要学一个东西，不是听听就算。
